# Drama Visual Studio — 角色与场景视觉工作室

一个技能完成从角色设计到生产提示词的整条链：**设计模式**负责「这个人是谁、穿什么」，**生产模式**负责「设定图、入景、场景变更、扩图、资产链」，**审查模式**负责返图纠偏。默认输出文本，不生成图片；MJ 默认英文，GPT-image2 沿用用户指定语言或当前请求语言。

新建图像统一走一套高级半写实 3D CG 视觉体系：人物精致风格化，场景自然写实，两者共用同一套渲染基础、光照规律、材质体系、色彩管理和电影级后期。表现方式可以不同，但不能像来自两个世界。

本文件只做导航和安装说明。**规则以 `SKILL.md` 与 `references/contract/` 为准**，这里不重复。

## 四种模式

| 模式 | 什么时候用 | 交付 |
| --- | --- | --- |
| **设计模式** | 从概念设计新角色、服装或设定图 | 批次向量 + 锁定行 + 7 点中文蓝图 + preflight 计数 + 英文提示词 + 排除项 + 可选角色记录 |
| **变体模式** | 给已有角色换装、换发型、加饰品、换场合 | 锁定行（剪影与主色标注为继承）+ 7 点蓝图（第 2、7 点改写）+ preflight 含变体完整性 + 一条提示词 + 账本 `↳` 行 |
| **生产模式** | 已有设计，要做具体产物 | 简短交接说明 + 一条提示词 |
| **审查模式** | 收到返图，检查是否偏移 | 观察到的差异 + 局部修正提示词 |

## 两条贯穿全包的分界

这两条是本包防止「每个角色长得一样」「每套服装同一模板」的机制，也是使用前必须先理解的部分。

**一、craft 与 decision 分开。** 渲染工艺（眼睑线、虹膜纤维、瓷面光泽、发丝成束）是 craft，逐字复用、全组共享；身份决策（面部指数、口宽、眼距、虹膜填充率、唇比）是 decision，每个角色必须从自身的 Position 事实独立推导。把 craft 串放进 decision 位，就是同质化的机械原因。判据：**这句话第二个角色能不能原样用？** 能，就是 craft，decision 还没写。定义见 `contract/gates.md` §8。

**二、设计不是单角色事件，但「新角色」和「同一角色的第二套造型」是两套规则。** 单角色检查永远看不到批次——每张图单独看都成立。动笔前必须读批次账本（`contract/records.md` §8），并先判定这次是新角色还是变体：

| | 新角色 | 同一角色的变体 |
| --- | --- | --- |
| 剪影 / 主色 | 必须避开所有已有行（硬失败） | **继承**，不参与比对 |
| 身份集 | 从 Position 事实推导（`face.md` §2A） | **逐字复用记录，不得重推** |
| 判据 | 九轴中至少五轴不同 | 四个 look 因素中至少三项不同 |
| 账本 | 新增 cast 行 | 加 `↳` 变体行，不占用剪影/主色槽位 |

把新角色的规则套到换装上，会要求角色"不要长得像自己"——这正是变体模式存在的理由。定义见 `contract/gates.md` §9 与 §9A，流程位置是 `pipeline/design.md` 的 Layer 0 与 §1 Mode C。

## 关键流程

**种子从剧本冲突推导，不从种子库挑。** `bank/costume.md` §1C 是五步程序：命名冲突（不是角色）→ 命名它让身体每天做什么 → 命名强制或禁止的物件类 → 写成短隐喻 → 跑三条成长规则。§1B 的 25 个种子是校准集，示范「一个合格种子长什么样」，不是菜单。只有写给没有剧情的背景角色时才直接取用，并要在蓝图和账本里标注。

**身份集从角色事实推导，不从 register 预设取。** `bank/face.md` §2A 是五步程序，核心是先定三个锚定参数（面部指数、口宽、眼距），它们决定缩略图上的「是不是同一个人」。§3 的 register 预设降级为「无 Position 事实时的兜底」。

**密度是批次内的散开，不是达标线。** 层数、描边率、节点数、花型覆盖四个因素都有区间，但两个同 register 角色不能在四个因素上全部重合；未处理的边**集合**才是差异化所在。见 `bank/density.md` §8A。

**变体只设计 look 层，不重推身份。** 给已有角色换装时，身份块（十个面部参数、发际线、永久痕迹、体型、皮肤完成度）逐字沿用记录；`bank/face.md` §2A 的推导程序**不重跑**——重跑会产出另一个人。变体的种子从**这套衣服的场合**推导，而不是角色的整个人生。剪影与主色默认保留，只有角色的地位或身份真的变了才改，且必须在蓝图里说明理由。

**画幅按用途选，不按习惯选。** 竖屏短剧、漫剧、竖版封面用 9:16；场景底图与设定图用 16:9；单张角色肖像用 3:4。设定图是规格文档，首帧是镜头，两者画幅不同且不能互相裁切转换——详见 `bank/framing.md`。

## 加载量与文件规模

加载哪些文件由 `SKILL.md` 的 load contract 表决定。生产与审查路径最多读 4 个文件；**设计模式是唯一的重路径**，因为它要先读批次账本（`contract/records.md` §8），再走 6 层设计栈跨六个知识域（truth / face / costume / form / material / density），每层各需一个来源。

当前最大三个文件：`contract/visual.md`（33 KB）、`pipeline/design.md`（30 KB）、`demos.md`（31 KB）。前两个通读也成立，不拆分：`visual.md` 的十二节之间是引用关系而非并列查表，`design.md` 是唯一流程主干。`bank/costume.md`（25 KB）是母题、拓扑、肌理、发型、群像五组独立查表，按需读小节即可。

## 维护约定

1. **一条规则只有一个家。** 新增或修改规则时，写进 `contract/`；其他地方只写「见 contract/x §n」。同一句规则出现两次，就是一次待修的重复。
2. **7 点蓝图不可省略。** 缺任一点即为未完成设计。第 5 点（装饰密度）必须给出层数、描边率、节点数、花型覆盖的具体数字，写成形容词等于没写。第 7 点写推导出的身份集数值，不写「精致」。
3. **craft 与 decision 不能混。** 见上文分界一。
4. **设计不是单角色事件。** 见上文分界二。
5. **验收只有一个门，且分清两种检查。** `pipeline/design.md` §6 是唯一交付门槛，其中「计数」项用 `scripts/preflight.py` 跑，「判断」项（剪影可读性、明度层次、脸是否赢、是否好看、**这张脸是否像上一个角色**）必须用眼睛看，不得用脚本结果冒充。
6. **不写历史。** 文档只描述当前状态，不记录「上一版是什么样」「改了什么」。变更历史在 git 提交里。

## 机械校验

`scripts/preflight.py` 是可计数的那一半。它输出词数、配色与材质词频（对照 accent 2 / anchor 4 / base 8 / 材质 5）、禁用词、`--no` 合规性、craft 元素是否齐备、身份集是否推导，以及配合账本时的批次向量对比，失败返回非零。

```bash
python -I scripts/preflight.py prompt.txt --register editorial
python -I scripts/preflight.py prompt.txt --register glamour --palette
python -I scripts/preflight.py prompt.txt --register glamour \
    --ledger batch.txt --vector "cocoon · umber · languid · glamour gear 2 · dir2 · warm-gi · rope piping · rope-knot · facial 1.30"
python -I scripts/preflight.py variant.txt --register glamour \
    --ledger batch.txt --variant-of "A 女主" --inherit \
    --vector "topology 5 骨相紧束 · 珠白缎镶边 · 团花缠枝 · 节点聚于发冠"
```

用 `--ledger` 时一并给 `--vector`：向量从蓝图取，因为提示词正文只能暴露九轴里的三四个，单靠正文会低估差异。`--variant-of` 切到变体模式，豁免轴 1/2，`--vector` 改为四个 look 因素；加 `--inherit` 则反向校验剪影与主色是否仍与角色一致——防止把新角色伪装成变体来绕过轴 1/2。它看不到「好不好看」，也看不到「这张脸是否像上一个角色」——那些仍然要人判断。

## 使用示例

- 角色设计：`仙侠 / 世家血脉 / 骨白配朱砂 / 沙漏 / gear 2 / editorial。设计一位失去宗门、仍守着礼数的莲修 goddess。`
- 竖屏首帧：`设计一位短剧女主的竖屏首帧，9:16，雨夜，冷光，脸在上三分之一。`
- 设定图：`根据这个角色记录生成身份设定图提示词，MJ，16:9。`
- 非重要角色：`设计一位次要角色，成年人类驿站管理员，深棕短发，靛蓝工作外套和皮革腰包。直接给我 GPT-image2 设定图提示词，参考附件重要角色设定图的画风。`
- 场景：`黄昏的树屋村落，不要人。`
- 场景变更：`基于这张 MJ 村落底图，给我 GPT-image2 雨夜版提示词，保留机位与建筑道路结构，亮起已有窗户的灯光。`
- 角色入景：`按角色记录把角色放在桥头，保留雨夜状态和村落结构，用 GPT-image2。`
- 同场景换机位：`参考这张底图，从桥头看向水车，保持建筑形制与空间连接。`
- 返图修正：`对比原图和这张雨夜返图，窗户多了一扇，门前木桶也回来了。给我局部修正提示词。`
- 扩图：`保留水墨笔触，只补全被裁掉的斗篷和袖口，不扩成全身。`
- 审查：`对比设定图和这张返图，指出偏移，先只给观察，不改图。`

解压后保留顶层 `drama-visual-studio/`，放入宿主支持的技能目录。ZCode 可使用项目或用户级 `.agents/skills/`；是否支持直接上传 ZIP 由宿主决定。

## 验证

文本模拟与结构检查用于检查规则执行、YAML、链接和包内容。真实出图另需检验：设计模式的概念到设定图、生产模式的同一角色多产物、同机位昼夜/天气变体、加人、移除物件、同地点换机位、返图纠偏；对比结构、状态继承、画风和未知区域的处理，记录偏移及修正结果。未执行实图测试时不据此证明头身比、身份、多视图一致性、像素保持或文字精度。

这条同样适用于本包自身：`contract/` 的一次性归位可以靠链接检查和重复度检查验证，但「同一个角色在多张图里长得一样」「改完之后出图真的更多样」不能靠文件结构证明。批次账本与身份集推导解决的是结构缺陷，不是结果保证。
